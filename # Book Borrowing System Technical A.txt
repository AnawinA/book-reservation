# Book Borrowing System: Technical Architecture and Coding Blueprint

**Target engineer:** DeepSeek V4.1 (Lead Software Engineer)
**Course:** KMITL Server-Side Web Development (Units 1–14)

## How to use this blueprint

1. Paste the **Master Context Prompt** into DeepSeek once, at the start of the session.
2. Then paste the Phase 1 to Phase 7 prompts in order. Each phase builds on the code from the phase before it.
3. After each phase, run that phase's **verification gate** before you move on.
4. If DeepSeek's output gets cut off, reply `CONTINUE FROM: <last file path>`. Every prompt tells it to stop only at the end of a file.

## Architectural Decision Records (ADRs)

Your spec leaves four things open. You need to decide these now, because each one changes the code.

| ADR | Problem | Decision | Trade-off |
|---|---|---|---|
| **ADR-1: Shop ownership** | The `users` table can't link an OwnerShop user to a shop, so any owner could manage any shop. | Add a nullable column `users.shop_id` (foreign key to `shops.id`). It's still 6 tables. RBAC checks `req.user.shopId === :shopId`. | This is the only change to the schema. If your instructor forbids it, remove the column and the shop-scope check. |
| **ADR-2: Reward claim code** | `PATCH /rewards/claim` needs a code, but no table stores redemptions. | When a customer redeems, the server issues a **signed voucher** (an HS256 JWT signed with `REWARD_CODE_SECRET`, valid for 72h, containing `uid, rid, sid, jti`). The claim endpoint checks the signature, expiry, shop and reward. | A voucher can be claimed more than once while it's valid. Write this down in the README as a known limitation, with a 7th `reward_redemptions` table as the future fix. |
| **ADR-3: Where transactions live** | Business logic that touches several tables needs one place for its transaction. | Models run the transactions through `withTransaction(fn)` in `configs/db.js`. It sends literal `START TRANSACTION` / `COMMIT` / `ROLLBACK` statements and locks rows with `SELECT … FOR UPDATE`. | Controllers stay thin, and the logic can be unit-tested with a mocked connection. |
| **ADR-4: Test isolation** | Integration tests shouldn't need a live MySQL. | Split `app.js` (the app factory) from `index.js` (which starts listening). Integration tests use Supertest with `jest.mock()` on the model modules. Unit tests mock `configs/db`. | `npm test` runs anywhere, including CI. The real database is checked by the Docker smoke test in Phase 7. |

## Phase 1: Foundation, Tooling and Containerization

### 1. Summary and objective
This phase creates a runnable, containerized skeleton with nothing in it yet:
- Config loaded from `.env` and checked at startup.
- A MySQL connection pool (`mysql2/promise`) and a transaction helper.
- JWT utilities.
- A central error handler and a health endpoint that uses Node core modules.
- Docker Compose running the app and MySQL, with a healthcheck and the `db_data` volume.

**Covers:** Units 1, 2, 3, 4, 6 (dotenv), 8 (pool).

## Phase 2: Database Schema, Seed and SQL Evidence

### 1. Summary and objective
This phase builds the full relational schema with foreign keys, indexes and CHECK constraints. It adds an idempotent Node seeder (bcrypt hashes are computed at runtime, never hard-coded). It also includes a reference SQL file showing DDL, DML, joins, aggregates and TCL, which the grader can inspect.

**Covers:** Units 6, 7.

### 2. Files and specs

| File | Spec |
|---|---|
| `db/init.sql` | Creates the 6 tables in foreign-key order: `shops`, then `users`, `book_collections`, `campaigns`, `rewards`, `book_items`. Includes indexes and CHECK constraints. |
| `scripts/seed.js` | Idempotent. Hashes passwords with bcrypt. Seeds shops, users (Admin, 2 owners, 2 customers), 6 collections, campaigns (one active, one expired), rewards (one out of stock), items (one overdue borrow). |
| `db/sample-queries.sql` | Annotated DML, JOIN, GROUP BY/aggregate, soft delete and a full TCL example |

## Tips for running DeepSeek

- **Pin the context:** if DeepSeek starts drifting (for example, it switches to `bcryptjs` or ES modules), paste the Master Context again before continuing.
- **Contract drift:** in Phases 5–7, if DeepSeek calls a model function by the wrong name, point it to the signatures in Phase 3. Those signatures are the source of truth.
- **Before submitting:** run `docker compose down -v && docker compose up --build`, then `npm test`. The first command checks the real database. The second checks the logic and API without one.
- **If your instructor rejects ADR-1:** drop `users.shop_id` and `requireOwnShop`. Everything else still works, but owners are no longer limited to their own shop. Mention this in the README.
